Every page has the same 3 parts
  1. Sidebar (<aside class="sidebar">): menu links. The current page link has class active.
  2. Topbar (<header class="topbar">): page title and user name.
  3. Content (<main class="content">): the cards, tables and forms of that page.
Bootstrap words used
  • row + col-md-3 → make columns (12 columns = full width).
  • card → white box with border. table → nice table. btn btn-primary → blue button.
  • data-bs-toggle="modal" data-bs-target="#addModal" → opens the pop-up form. No JS needed.
  • data-bs-dismiss="modal" → closes the pop-up.
  • data-bs-toggle="tab" → switches tabs on the faculty page.
  • mb-3 = margin bottom, me-1 = margin right, d-none = hide, ms-auto = push to the right.
How the "backend" buttons work

Any button that needs the server has:

<button onclick="callBackend('POST /api/faculty', 'Save new faculty')">Save</button>

callBackend() (in js/app.js) shows a dark pop-up in the bottom right: "Backend will be called here" + the API name. It also prints it in the browser console (F12). All tables currently show sample data typed directly in the HTML.

Form inputs have a name="...". That name is the exact field name the backend will receive (for example name="maxHours").

Part 3 - Prompt for the backend team

Copy this and paste it into Claude (or any AI) together with this project folder.

You are helping college students build the BACKEND for a "Timetable and Faculty Workload Management System" for an engineering university. The FRONTEND is already finished (plain HTML + CSS + Bootstrap 5 + one small file js/app.js). Do not change the look of any page.

GOAL
Build a simple Python Flask backend and connect it to the existing frontend. Code must be beginner level: easy to read, short functions, lots of comments, no advanced patterns.

TECH
- Python 3, Flask, flask-cors, SQLite (built-in sqlite3 module, no ORM needed).
- Files: app.py (all routes), database.py (create tables + sample data), timetable.db.
- Serve the frontend HTML files from Flask too (static folder), so there are no CORS problems.
- All APIs send and receive JSON.

DATABASE TABLES
- users (id, username, password, role 'admin'/'faculty', faculty_id)
- faculty (id, name, email, department, designation, maxHours)
- subjects (id, code, name, type 'Theory'/'Lab', hoursPerWeek, department)
- rooms (id, name, type 'Classroom'/'Lab', capacity, building)
- sections (id, name, department, year, strength)
- settings (days as JSON text, periods as JSON text [{no, start, end}])
- timetable (id, sectionId, day, period, subjectId, facultyId, roomId)
- leaves (id, facultyId, date, reason, substitutes as JSON text)
Add the same sample data that the HTML pages show (Dr. Anitha Raman, Ms. Priya Venkatesh, Mr. Arun Kumar, CS101, MA101, A-101, Lab-1, CSE-A, CSE-B, etc.). Demo users: admin/admin123 and priya@college.edu/faculty123.

APIs TO BUILD
1. POST /api/login  {username, password, role} -> {ok, role, user}
2. GET /api/dashboard -> counts (faculty, subjects, classes per week, clashes), clash list, workload list, today's classes
3. CRUD for faculty, subjects, rooms, sections:
   GET /api/  (optional ?search=), POST /api/, PUT /api//, DELETE /api//
4. GET /api/settings, PUT /api/settings
5. GET /api/timetable?section= or ?faculty= or ?room=
6. POST /api/timetable {sectionId, day, period, subjectId, facultyId, roomId}
   BEFORE saving, check clashes on the same day + period:
   - room clash: same room already booked
   - faculty clash: same faculty already teaching
   - section clash: same section already has a class
   If clash -> return 409 {ok:false, message:"Faculty clash: Mr. Arun Kumar already teaches CSE-B on Monday P2"}
   Else save and return {ok:true}
   DELETE /api/timetable/
7. GET /api/clashes -> all clashes in the whole timetable + warnings (room capacity smaller than section strength, Lab subject in a non-lab room, faculty over maxHours)
8. GET /api/workload (optional ?department=) and GET /api/workload/
   For each faculty: theory hours, lab hours, total = number of timetable slots, maxHours, utilisation %, status:
   Overloaded if total > maxHours, Underloaded if total < 60% of maxHours, else Optimal.
9. Staff leave: GET /api/leaves, POST /api/leaves {facultyId, date, reason, substitutes}, DELETE /api/leaves/
   GET /api/substitutes?facultyId=&date= -> for each period that faculty teaches on that weekday, list other faculty who are free in that period and not on leave and not overloaded.
10. CSV downloads: GET /api/timetable/csv, /api/workload/csv, /api/reports/csv

CONNECTING THE FRONTEND
- In js/app.js, the function callBackend(api, message) is a placeholder that only shows a pop-up. Every button that needs the server already calls it, for example:
  onclick="callBackend('POST /api/faculty', 'Save new faculty')"
- Replace the placeholders with real fetch() calls, page by page. Form inputs already have name="..." attributes that match the API field names above.
- Replace the sample table rows in each HTML page with rows built from the GET API data (simple JavaScript loops with innerHTML, one small JS file per page is fine, e.g. js/faculty.js).
- In login() in js/app.js, replace the hard-coded checks with POST /api/login, then save the user in sessionStorage.
- Show success / error using the same pop-up style (class "api-popup" in css/style.css).

DELIVER
- Full code for app.py and database.py with comments explaining each part for beginners.
- requirements.txt
- Steps to run: pip install -r requirements.txt, python database.py, python app.py, open http://localhost:5000
- A short test list: how to test each API with the browser or Postman.
